# Bread Pitt Bake Model

## Purpose

This document defines the canonical content and publication contract for a
Bread Pitt bake. It is based on the completed Bake001 workflow and establishes
the source-of-truth boundaries required before Bake002.

The model keeps authored content readable, generated artifacts reproducible,
and publication state verifiable. A fact should have one authoritative owner.
Other files may reference that fact by stable identifier but must not maintain
independent copies of it.

## Bake Workspace

Each bake uses this canonical workspace:

```text
content/bakes/<year>/<bake-id>/
├── bake.yml
├── photos.yml
└── story.md
```

Generated manifests may be stored beside the canonical files for review, but
they are not authoring surfaces:

```text
content/bakes/<year>/<bake-id>/
├── media-intake.json       # generated
└── media-publication.json  # generated by abbey media publish
```

Canonical prepared media and public derivatives remain separate:

```text
working/media/bakes/<year>/<bake-id>/  # canonical prepared media
public/images/bakes/<year>/<bake-id>/  # generated public derivatives
```

Raw camera files under `media/` are preserved inputs. They are not selected
for publication merely because they exist.

## Authority by Concern

| Concern | Authoritative source | Consumers |
| --- | --- | --- |
| Bake ID, title, tagline, dates, status, rating, result, and lessons | `bake.yml` | Bake index, bake page, validation |
| Public route | `bake.yml` | Astro route generation, indexes, recipe backlinks, site validation |
| Recipe relationship | Recipe slug in `bake.yml` | Bake page, recipe page, recipe index |
| Starter relationship | Starter identity in `bake.yml` | Bake page |
| Hero selection | Photo ID in `bake.yml` | Bake page, bake index, recipe presentation |
| Authored narrative | `story.md` | Shared bake renderer |
| Editorial photo selection, stable photo IDs, captions, groups, and positions | `photos.yml` | Story renderer, intake generator, validation |
| Original-to-prepared filename provenance and capture date | Abbey rename manifest | Intake generator and validation |
| Media publication inputs | Generated `media-intake.json` | `abbey media publish` |
| Derivative paths, dimensions, fingerprints, transformations, and privacy results | Generated `media-publication.json` | Bake renderer, site validation |
| Public image bytes | Generated files under `public/images/bakes/` | Built website |

## Canonical Files

### `bake.yml`

`bake.yml` owns the structured bake record.

Required concepts for the current model are:

- Schema version.
- Stable bake ID.
- Title and tagline.
- Started and completed dates.
- Status.
- Recipe slug.
- Starter relationship.
- Result summary.
- Lessons.
- Hero photo ID.
- Public route.
- Relative references to `story.md` and `photos.yml` when explicit references
  remain useful.

Rating and internal temperature are optional result facts. A scaffold must use
explicit empty values or omit optional facts rather than inventing them.

The recipe slug is the relationship key. Recipe title, route, featured-bake
title, bake route, and representative image should be resolved from canonical
records rather than maintained as reciprocal copies.

The hero is owned only by `bake.yml`. It must reference a photo ID declared in
`photos.yml`.

### `story.md`

`story.md` owns the authored narrative and its placement of editorial media.
It may contain headings, prose, links, and the supported photo directives.

The story references photos by stable photo ID:

```text
{{ photo: final-loaf }}
{{ gallery: fold-1 }}
```

A `photo` directive must resolve to exactly one `photos.yml` entry. A `gallery`
directive resolves the entries in a named group. Gallery layout is configured
in `photos.yml`; a comparison layout requires exactly two entries, while a grid
may contain any number of entries.

Story front matter identifies the owning bake. Title and tagline belong in
`bake.yml`; the renderer supplies them to the page.

### `photos.yml`

`photos.yml` owns editorial selection and presentation metadata. Each entry
contains:

- A stable photo ID unique within the bake.
- The prepared image filename from the canonical working-media directory.
- A human-authored caption.
- Optional grouping and position metadata used by story directives.

The prepared filename must map to exactly one entry in the Abbey rename
manifest. That join supplies the original camera filename and capture date for
the generated intake manifest.

`photos.yml` does not own the bake hero, derivative path, transformation
settings, source fingerprint, or privacy-validation result.

## Generated Artifacts

### `media-intake.json`

The intake manifest is generated deterministically from:

- Editorial selection and captions in `photos.yml`.
- Original-to-prepared filename provenance and capture dates in the Abbey
  rename manifest.

Its item order follows `photos.yml`. It must not be edited by hand. Generation
must fail before writing if a selected prepared image has no unique rename
mapping, a source file is missing, or identifiers and destinations conflict.

An unchanged regeneration must be byte-for-byte stable and leave the existing
file untouched. Validation must detect when the generated artifact is missing
or stale relative to its canonical inputs.

### `media-publication.json`

The publication manifest is generated by `abbey media publish`. It records the
verified relationship between canonical prepared media and privacy-safe public
derivatives, including fingerprints and transformation facts.

It is a versioned pipeline contract, not an authoring surface. Corrections are
made in canonical metadata, media configuration, or the publisher and then
regenerated.

### Astro output

Bake pages are build artifacts rendered from `bake.yml`, `story.md`,
`photos.yml`, recipe data, and the publication manifest through shared Astro
code. A bake must not require a hand-written Astro page.

The renderer must resolve public images through publication-manifest entries
rather than reconstructing derivative paths from filenames alone.

## Relationship Rules

### Bake to recipe

The recipe slug in `bake.yml` is authoritative. Recipe pages and indexes derive
featured or related bakes by querying bake records. Recipe data may eventually
provide an explicit image override, but it must not duplicate a bake backlink
as the normal relationship.

### Bake to starter

`bake.yml` owns the starter relationship. The current model permits a named
starter and route because the site has one starter profile. A stable starter ID
should replace the name as the relationship key if multiple starters are
introduced.

### Bake to photos

`bake.yml` and `story.md` reference photo IDs. `photos.yml` maps those IDs to
canonical prepared media and captions. The publication manifest maps prepared
media to verified derivatives.

No canonical file should reference a public derivative path directly.

## Bake001 Inventory

Bake001 now uses the canonical renderer, generated index, recipe relationship,
publication-manifest image resolution, and generic gallery directives. Its
`media-intake.json` remains a generated artifact derived from `photos.yml` and
the rename manifest.

## Validation Contract

A complete bake validator should eventually verify:

- Supported schema versions.
- Required canonical files and fields.
- Unique bake ID and public route across all bakes.
- Valid dates, status, rating scale, and optional result facts.
- Existing recipe and starter relationships.
- Unique photo IDs and prepared filenames.
- Existing prepared media and unique rename-manifest mappings.
- Valid story photo and gallery directives.
- A hero photo ID that resolves to one selected photo.
- Fresh intake generation.
- Publication-manifest ownership, source integrity, derivative existence, and
  privacy assertions when publication is required.
- Recipe and index presentation derived from canonical relationships.
- Absence of a hand-written per-bake Astro route.

Canonical validation should be runnable before media publication. Publication
readiness checks may require generated manifests and derivatives and should be
reported as a distinct validation layer.

## Evolution Policy

The Bake001 shape is the first validated version of this model. Extend it only
when a real bake requires another concept. Keep bake-specific semantics in
Bread Pitt until another Abbey domain demonstrates an equivalent reusable
contract.
